# DukaanOS — Deployment

DukaanOS is a single Cloudflare Worker (vinext = Next.js App Router on Vite) with D1, R2,
Workers AI and Rate Limiting bindings, plus a daily cron trigger. There are **no secrets
to manage for the core app** — every integration is a binding.

## 1. Prerequisites

- Node 20+ and pnpm 10+
- A Cloudflare account on the **Workers Paid plan** (D1 allows 1,000 queries per request on
  paid vs 50 on free; a large bill or CSV import runs many statements in one request)
- `npx wrangler login` (or `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` in CI)

## 2. One-time setup per environment

```bash
pnpm install
# Staging
npx wrangler d1 create dukaanos-staging
npx wrangler r2 bucket create dukaanos-staging-files
# Production
npx wrangler d1 create dukaanos-prod
npx wrangler r2 bucket create dukaanos-files
```

Paste each `database_id` into `wrangler.jsonc` under `env.staging` / `env.production`
(replacing `REPLACE_WITH_…`). Set `APP_URL` to the real hostname for each environment.

Rate limiting uses the Workers Rate Limiting binding (`AUTH_LIMITER`, `AI_LIMITER`); the
`namespace_id`s in `wrangler.jsonc` just need to be unique integers per account.

### Optional: password-reset email

1. Onboard your domain: `npx wrangler email sending enable yourdomain.in`
2. Add to the environment in `wrangler.jsonc`:
   ```jsonc
   "send_email": [{ "name": "EMAIL" }],
   "vars": { …, "EMAIL_FROM": "no-reply@yourdomain.in" }
   ```
Without it, reset links are only logged in development; in production owners reset staff
passwords from **Settings → Users** (OTP / WhatsApp delivery is a planned extension).

## 3. Migrations

Migrations live in `migrations/` (generated by `drizzle-kit`, plus a hand-written migration
for the stock-guard trigger and reference data). They are forward-only and additive.

```bash
pnpm db:migrate:staging      # wrangler d1 migrations apply dukaanos-staging --remote --env staging
pnpm db:migrate:production   # wrangler d1 migrations apply dukaanos-prod --remote --env production
```

Changing the schema: edit `src/server/db/schema.ts` → `pnpm db:generate` → review the SQL →
commit → apply to staging → deploy → verify → apply to production → deploy.

## 4. Deploy

```bash
pnpm check                 # typecheck + lint + unit/integration tests + build
pnpm test:e2e              # Playwright against the production build
pnpm build && pnpm deploy:staging
pnpm build && pnpm deploy:production
```

The cron trigger (`30 15 * * *` = 21:00 IST) sends daily summaries and weekly udhaar
reminders, and cleans up expired sessions / idempotency keys / AI proposals.

## 5. Local development

```bash
cp .dev.vars.example .dev.vars
pnpm db:migrate:local
pnpm db:seed:local         # demo "Sharma General Store" (30 days of data)
pnpm dev                   # http://localhost:3100
```

Demo logins (local only): owner **98765 43210 / dukaan123**, staff **98765 00001 / staff1234**.

The Workers AI binding always calls Cloudflare (it is `remote: true`), so local voice/LLM use
needs `wrangler login`. Without it the assistant still works: common commands are parsed by
the built-in rules parser, and the LLM step is skipped.

Test the cron locally against a production build:

```bash
pnpm build && npx wrangler dev --config dist/server/wrangler.json --test-scheduled --persist-to .wrangler/state
curl "http://localhost:8787/cdn-cgi/handler/scheduled?cron=30+15+*+*+*"
```

## 6. Observability

- Workers Logs is enabled (`observability.enabled`). Every request logs one JSON line with
  `requestId`, `path`, `status`, `ms`, `userId`, `businessId`; secrets are redacted.
- AI interactions are stored in `ai_interactions` (intent, parser, confidence, latency, status).
- Every mutation writes `audit_logs` in the same database transaction.

## 7. Backups & disaster recovery

| Layer | Mechanism |
|---|---|
| Point-in-time | D1 Time Travel keeps 30 days: `npx wrangler d1 time-travel info dukaanos-prod` then `npx wrangler d1 time-travel restore dukaanos-prod --timestamp=<unix>` |
| Nightly export | `npx wrangler d1 export dukaanos-prod --remote --output=backup-$(date +%F).sql` (run from CI, store the file in R2 or elsewhere off-account) |
| Per-business | Owners can export products, sales, purchases, customers, suppliers and expenses as CSV from **Settings → Data** |
| Files | Product photos live in R2 (`FILES`); enable R2 object versioning or replicate the bucket |

## 8. Rollback

- **Code:** `npx wrangler rollback --env production` (or pick a version in the dashboard). Because
  migrations are additive, the previous version keeps working against the newer schema.
- **Data:** D1 Time Travel restore (above). Restore to a *new* database first if you only need to
  recover specific rows, then copy them back.
- **Bad migration:** write a new forward migration that fixes it; never edit an applied one.

## 9. Production checklist

- [ ] `database_id`s and `APP_URL` set for the environment
- [ ] Migrations applied (`wrangler d1 migrations list … --remote`)
- [ ] Custom domain attached (HTTPS is required for microphone access and secure cookies)
- [ ] Workers Paid plan
- [ ] Optional email sending configured
- [ ] Smoke test: sign up, onboard, create a sale by voice, check the audit log
